# EV-FEAT-01 因子扩容：数据可行性核实与方案设计

日期：2026-09-22

## 结论先行

1. `raw_payload` 的 `endpoint='statistics'` 中实际出现了 19 个
   `statistics[].type`。`Shots on Goal`、`Shots off Goal`、`Total Shots`、
   `Corner Kicks`、`Ball Possession` 在生产样本中总体为 99.9%–100.0% 非空，
   因此射门、角球、控球率字段确实存在且具备数据可行性。`expected_goals`
   总体约 91.3%，但有联赛差异；`Red Cards`（19.4%）和 `Free Kicks`（2.6%）
   不适合作为稳定候选。所有覆盖率均按球队对象观测计，不把重复抓取误称为独立比赛覆盖。
2. `team_xg_match.opponent_team_id` 非空为 `22,830/22,830 = 100.00%`。
   必须区分两个口径：只按 `kickoff_at` 的运行时历史深度 `<3` 为
   `1,622/22,830 = 7.10%`；严格要求历史行的 `captured_at < target kickoff` 后，
   `<3` 为 `21,688/22,830 = 95.00%`。前者适合描述“按比赛时间已有多少历史”，后者才是
   当前数据可用于严格 PIT 训练/回测的真实可见性口径。
3. 对手强度可以在不使用未来结果的前提下做赛前滚动特征。推荐先做方案 A（联赛内
   `xG against` 分位数），方案 B（带先验收缩的递归 rating）作为离线对照；本轮不实现。
4. `squad_value_mapping` 目前是占位 task：它不调用 API-Football、Transfermarkt 或任何
   其他上游系统，也没有逐场 PIT 估值产物。当前 `ApiFootballClient` 仅被 fixtures/h2h
   两个 task 使用。

## 1. statistics payload 实测

### 1.1 查询口径

- 数据库：生产 PostgreSQL `w2`，只读连接；表 `raw_payload`。
- 过滤：`endpoint='statistics'`，解析每条 payload 的 `response[].statistics[]`。
- 分母：每个球队对象的一次 field observation；非空 `value` 为覆盖分子。
  因而重复抓取会增加观测数，不能直接解释为去重后的独立比赛数。
- 本次原始统计汇总：13,192 条 raw statistics 行、12,699 个 fixture 参数；解析出的
  球队对象观测为 15,004（约 7,502 个球队对象成对的 fixture-equivalent）。另有
  7,510 个可通过当前 identity 映射得到的最新 fixture 记录，映射不完整，故不把它
  当作全量覆盖率分母。
- `—` 表示该联赛样本中该 type 没出现或没有可计算分母；`n<20` 表示球队对象数小于
  20，仅作存在性/方向描述，不据此做稳定性结论。

## 2. opponent_team_id 与冷启动

### 2.1 全局覆盖

`team_xg_match` 共 22,830 行，`opponent_team_id IS NOT NULL` 且去掉空白后为
22,830 行，故：

```text
opponent_team_id coverage = 22,830 / 22,830 = 100.00%
```

这是身份字段覆盖，不代表对手历史强度已可计算。

### 2.2 两个冷启动口径（更正）

#### A. 运行结构口径：只按比赛时间排序（7.10%）

这是“如果系统已经拥有这些历史行，按比赛时间看球队经历了多少场”的运营描述，
也就是把历史回补行视为在目标比赛前可用、但不检查其实际捕获时间：

```text
history_depth < 3  = 1,622 / 22,830 = 7.10%
history_depth >= 3 = 21,208 / 22,830 = 92.90%
```

它可用于估计联赛赛季初/升班马的结构性冷启动，但不能证明当时模型已经看到了这些行。
因此它**不是当前生产 materializer 的真实可见率**：`src/w2/features/xg_materialization.py`
实际同时检查 `row.kickoff_at < cutoff` 与 `row.captured_at < cutoff`。

适用场景是生产实时运行的**结构代理**：只有在实时采集确实发生在开球前时，才可把
7.10% 解释成生产冷启动率；本次历史回补本身没有证明这一前提。

#### B. 严格 PIT 训练/回测口径：比赛时间和可见时间双重约束

对每一行目标比赛，只计入同 `team_id`、`kickoff_at < target kickoff` **且**
`captured_at < target kickoff` 的历史行：

```text
history_depth < 3  = 21,688 / 22,830 = 95.00%  (strict PIT cold start)
history_depth >= 3 = 1,142 / 22,830 = 5.00%
```

这是当前批量回补数据能支持的严格 PIT 可见性，也是当前 materializer 在这批数据上的
有效生产口径。若未来生产在每场开球前及时采集，实时冷启动率可低于 95.00%；但当前
回补数据不能假定这些行曾在比赛前可见。

因此两个数字的验收含义是：

| 口径 | 冷启动 `<3` | 可用于 ≥3 场严格 PIT 特征的比例 | 适用场景 |
|---|---:|---:|---|
| 只按 `kickoff_at`（7.10%） | 7.10% | 92.90% | 生产实时结构代理；需实时采集时序另行证明 |
| `kickoff_at` + `captured_at`（95.00%） | 95.00% | 5.00% | 当前历史数据的严格 PIT 训练/回测 |

以对手强度窗口衡量可用训练量，严格 PIT 下：

| 特征最低历史要求（双方） | 球队行数 | 独立比赛数 | 占全部比赛行的比例 |
|---|---:|---:|---:|
| 双方各 ≥3 场 | 1,056 | 528 | 4.62%（按 22,830 行） |
| 目标与对手各 ≥5 场（方案 A 的首选窗口） | 1,008 | 504 | 4.41%（按 22,830 行） |
| 双方各 ≥8 场（方案 A 的敏感性窗口） | 962 | 481 | 4.21%（按 22,830 行） |

“独立比赛数”按 `fixture_id` 去重；行比例的分母仍是 `team_xg_match` 的球队行，不能
误读为比赛比例。

### 2.3 原始查询复核与错误说明

原先得到 7.10% 的实际 SQL 如下（从本次任务的执行记录恢复）：

```sql
WITH x AS (
  SELECT t.*, COALESCE(NULLIF(f.competition_id,''),m.competition_id) competition_id
  FROM team_xg_match t
  LEFT JOIN fixtures f ON f.id=t.fixture_id
  LEFT JOIN matchday_fixture_identities m ON m.provider_fixture_id=t.fixture_id
), ranked AS (
  SELECT x.*, count(*) OVER (
    PARTITION BY team_id
    ORDER BY kickoff_at, captured_at, fixture_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) own_prior
  FROM x
), depths AS (
  SELECT r.*, count(*) OVER (
    PARTITION BY opponent_team_id
    ORDER BY kickoff_at, captured_at, fixture_id
    ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING) opp_prior
  FROM ranked r
)
SELECT count(*) total_rows,
       count(*) FILTER (WHERE own_prior < 3) own_cold_lt3
FROM depths;
```

确认：该 SQL **遗漏了** `captured_at < target kickoff` 条件；`captured_at` 只被用于排序，
不是可见性过滤。因此 7.10% 不能标为严格 PIT 冷启动率。它还按全局 `team_id` 分区，
并没有实现报告文字所说的“同联赛内”限制，故本报告不再把它用于 PIT 训练结论。

本次只读复核使用的严格条件是逐目标行的等价查询：

```sql
WITH d AS (
  SELECT t.id,
    (SELECT count(*) FROM team_xg_match h
     WHERE h.team_id = t.team_id
       AND h.kickoff_at < t.kickoff_at
       AND h.captured_at < t.kickoff_at) AS own_pit,
    (SELECT count(*) FROM team_xg_match h
     WHERE h.team_id = t.opponent_team_id
       AND h.kickoff_at < t.kickoff_at
       AND h.captured_at < t.kickoff_at) AS opp_pit
  FROM team_xg_match t
)
SELECT count(*) AS total,
       count(*) FILTER (WHERE own_pit < 3) AS own_cold_lt3,
       round(100.0 * count(*) FILTER (WHERE own_pit < 3) / count(*), 2)
FROM d;
```

这次生产只读复算返回：`22830 | 21688 | 95.00`。因此上一版报告把 7.10% 写成“严格
PIT”是口径错误，现已明确纠正。

补充时序事实：当前 `team_xg_match` 的 22,830 行中，`captured_at < kickoff_at` 的行数为
0；严格 PIT 的 1,142 行并不是“赛前采集的历史全量”，而是这些行在更晚目标比赛之前已经
被回补/采集到的极少部分。该事实解释了为什么按 `kickoff_at` 看似有历史，按真实可见时间
却只有 5.00% 达到自身 ≥3 场。

当前 fixture→league 的部分 identity 映射不完整（按联赛重算会出现大量 UNKNOWN），所以
本节正式验收数字采用全局 team_id/时间口径；不把 UNKNOWN 任意归入某个联赛。

## 3. 对手强度指数：设计草案（不实现）

两种方案都要求以目标比赛开球时间为 cutoff，禁止读取当前比赛结果、赛后统计或未来赛季
数据。两种方案均应输出 `value`、`history_n`、`cold_start`、`as_of`，让缺失与退化可审计。

### 方案 A：联赛内 rolling xG-against 分位数（首选、较简单）

- 对每个对手，截至 cutoff 取最近 `N=5`（敏感性对照 `N=8`）场已完成比赛的
  `xg_against` 均值；只在同联赛、同赛季优先，跨赛季需显式配置。
- 在同联赛的历史分布中将该均值转成 percentile（例如 0–1）；再把目标队近期所遇
  对手 percentile 的均值/加权均值作为对手强度特征。
- 目标球队自身历史 `<3`：不伪造强度值，返回 `value=NULL`、`cold_start=true`，调用方
  退化到当前纯 xG 均值/既有输入；不把联赛均值冒充球队观测。
- 对手自身历史 `<5`：同样返回缺失并保留 `history_n`，或仅在预先注册的规则下退化到
  联赛均值；必须带 `degraded=true`，不能静默混入正常样本。
- 预计量级（仅未来实现估算）：新增
  `src/w2/features/opponent_strength.py` 约 100–180 行；在既有 xG materialization
  处增加约 30–70 行接线；时序/冷启动单测约 100–180 行。此处没有创建这些文件。

### 方案 B：联赛先验收缩的递归 opponent rating（更稳健、复杂度更高）

- 为每个球队维护截至 cutoff 的递归 rating，例如近期 `xg_against`（可扩展为净 xG）
  相对联赛均值的偏离；以 `n/(n+k)` 向联赛先验收缩，建议初始 `k=5`，窗口可用最近
  8 场并按时间衰减。
- 每场结束后才更新 rating；当前比赛不能参与自己的 rating。跨赛季重置/衰减规则必须
  在离线协议中预注册。
- 自身历史 `<3` 或对手历史不足窗口：返回收缩后的联赛先验并设置
  `cold_start/degraded=true`；如果验收要求“缺失而非退化”，则直接返回 NULL，不能把
  先验误标为实测值。两种策略须在 OOF 评估前固定，不能看结果后切换。
- 预计量级（仅未来实现估算）：新增 rating 模块约 150–250 行；materialization 接线
  约 50–90 行；时序泄漏、跨赛季、收缩和冷启动测试约 150–250 行。风险高于方案 A，
  必须先做离线 OOF 数据质量评估。

### 3.1 基于严格 PIT 覆盖的训练量判断

结论是：**当前历史回补数据不足以支持稳定的 per-league 方案 A/B 拟合或验收。**
严格 PIT 只有 5.00% 的球队行达到自身 ≥3 场；使用推荐的双方 ≥5 场窗口只有约
504 场独立比赛，而且还要按联赛、赛季、主客方向拆分，很多格子会落到个位数或零。
方案 B 的递归 rating 还需要连续可见序列，因此比方案 A 更容易受批量回补造成的时间断层影响。

缺口可以按两个层次量化：

- 严格自身 ≥3 场的目标行缺 `21,688/22,830`（95.00%）；
- 双方各 ≥5 场（方案 A 的首选窗口）目前仅 504 场独立比赛。若将“1,000 场独立比赛”
  作为一个**待 Owner 预注册的 pooled baseline**，当前还缺 496 场；per-league 的缺口
  还要按每个联赛/赛季的最小格子样本量另行计算，不能用全局 504 场掩盖。

要补上这些缺口，至少需要：

- 为目标联赛持续在每场开球前采集并保留 `captured_at < kickoff_at` 的 xG/statistics；
- 在严格 PIT 样本上累积至少 5–8 个已完成窗口，且每个目标联赛/赛季保留足够的独立比赛，
  再按预注册的最小格子样本量决定是否合并层级；
- 不用事后回补行“补齐”历史窗口。现有 504 场只能作为数据质量诊断/接口试跑，不能作为
  per-league 训练和效果结论的证据。

若必须在当前数据上推进，只能先做全局或强收缩的描述性质量审计，并显式标记
`NOT_ESTIMABLE`；不得把方案 A/B 的候选值接入 λ、EV、推荐或安全门。建议优先积累前瞻
PIT 数据，再重新评估方案 A；方案 B 暂缓到存在连续 PIT 序列后。两者本轮均不接入 λ、EV、
推荐或安全门。
