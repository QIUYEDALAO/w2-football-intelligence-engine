# W2 上线「行为验收」方案（V2 · 2026-09-26）

> 定位：在「上线检测（代码正确性）」之外，补一层「行为验收（目标达成性）」。
> 核心：**代码改对了 ≠ 目标达成了**。每条裁决上线后，必须验证生产数据行为，不只验代码 diff + 测试 + a–h 回读。
> 来源：42a6e60b 翻车教训（回读 a–h 全 PASS、容器全 healthy、测试 122 过，但生产上验证信号 0 条、历史 2763 条仍以推荐展示——「系统活着」与「裁决生效」是两件事）。

## 顶层原则（铁律）

**历史 vs 新增永远分开。** 凡报「还有 N 条」，必追问「部署后新增几条」。历史存量可以保留，新增必须符合新规则。本次 TOTALS 失败即栽在 2763 条历史盖住了「动态路径仍在产新」这一事实。

## 四类裁决 → 四类验收标准

| 裁决类型 | 验收标准 | 判据 |
|---|---|---|
| **停 X**（停正向/停推送/停采集） | 新增 = 0 | **机会窗**：等「本该产生 X 的场景出现时，X 没产生」才算数（如停 TOTALS 正向 → 等下一场 TOTALS 评估，看它是否 NO_EDGE_CURRENT）。N 小时只作兜底上限，超过无评估则延期判定，不许判通过。 |
| **改 X**（改公式/阈值/口径） | 新口径正确 + 历史口径归属 | 新数据按新规则；**历史数据必须带「口径版本标记 + 查询解释规则」**（看历史用旧公式、看新增用新公式），不许拿新公式回头重算历史充数。 |
| **开 X**（开推荐/开验证信号） | 新增 > 0 且**值正确** | 逐字段核值，不只核存在（fade 方向必须 OVER、derived_from_evaluation_id 必须指向 UNDER 原评估、赔率必须来自同 capture 反向侧）。防「带水印的空组/错组」误判通过。 |
| **冻结 X**（冻结参数/边界） | 取值 = 冻结值 | 部署后取值与冻结值逐位一致（fade_delta=0.05、档位边界 0.05/0.02/0），防「顺手一改」静默漂移。 |

## 检查三步

1. **部署前**：记基线——关键指标当前值 + 时间戳（候选数/推送数/状态分布/冻结参数值）；
2. **部署后**：查生产数据，对比基线，只看**增量**（机会窗优先，N 小时兜底）；
3. **判定**：按四类标准逐条判定。

## 四条硬约束（防自欺，每条强制）

1. **验收 SQL 随裁决冻结**：裁决书里预写验收 SQL——任何人跑同一条 SQL 必须得到同一个数，查询即证据，不许执行方现场自编 SQL 自证；
2. **结果落不可变记录**：谁、何时、跑了什么 SQL、基线值、结果值——记录落库；**执行者 ≠ 实现方**（W2 纪律 9/10：同源测试不是独立 oracle，完成报告必须区分实现与独立评审）；
3. **组合裁决逐条独立判定**：任一不过即整体不过——防「开的新增 >0」掩盖「停的新增 ≠0」（本次 TOTALS 即 T1 停 + T2 开的组合，两条都挂）；
4. **观察期 ≥ 一个完整足球日**：跨比赛日，保证至少覆盖一个完整评估周期，否则「下一个评估周期」的机会窗可能根本没出现。

## L5 行为验收编号

| 编号 | 检查项 | 验收 |
|---|---|---|
| L5-1 | 停 X → 机会窗新增归零 | 本该产 X 的场景出现时 X 没产生；N 小时兜底 |
| L5-2 | 改 X → 新口径 + 历史归属 | 新增符合新规则 + 历史带口径版本标记 |
| L5-3 | 开 X → 值正确 | 新增 > 0 且逐字段核值 |
| L5-4 | 冻结 X → 逐位一致 | 部署后取值 = 冻结值 |

## 落地

每条裁决落地，交付物 = **代码 diff + 测试 + a–h 回读 + L5 行为验收结果**，四样缺一不可。
